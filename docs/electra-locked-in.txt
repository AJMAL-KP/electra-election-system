# Electra — Implementation Plan

This is the **implementation plan**, not a learning/documentation plan. The implementation strategy follows a strict **vertical slice implementation approach**: workflow by workflow, end-to-end, so that each slice produces complete working functionality across technical layers that can be exercised and verified immediately.

The plan incorporates the decisions we have now locked in: Django + PostgreSQL + Channels/Daphne, session authentication, booth-bound technical identities, WebSocket-only liveness, atomic multi-position ballots, eligibility rules, frozen election configuration, credential rotation, reconnection/resynchronization, and server-authoritative voting.

The SRS establishes the three-interface architecture, Django/Channels backend, HTTP/WebSocket split, booth-bound authorization, single-use authorization, transactional voting, live turnout and result publication.  

---

# Implementation Strategy — Vertical Slices

Implement Electra vertically, workflow by workflow.

Do NOT implement the entire backend first and the entire frontend afterward.

Do NOT create isolated models, services, WebSocket consumers, templates, or UI pages merely because they belong to a particular technical layer.

Instead, take one meaningful user workflow and make that workflow work end-to-end through the existing architecture.

For each vertical slice:

1. Identify the exact user workflow.
2. Trace the workflow through the existing architecture, data model,
   state machines, invariants, authentication and authorization rules.
3. Implement only the backend/domain pieces required for that workflow.
4. Implement the required frontend interfaces.
5. Implement WebSocket communication where that workflow requires it.
6. Connect the actual frontend to the actual backend.
7. Test the complete workflow with realistic state transitions.
8. Verify the relevant invariants and failure cases.
9. Only after the slice works end-to-end, move to the next slice.

Example:

DO NOT:
"Build all WebSocket functionality."

INSTEAD:
"Implement voter authorization from Officer Station to Voting Kiosk."

The complete slice should be:

Officer Station
→ identify/select eligible voter
→ server validates voter and election state
→ create the appropriate single-use authorization
→ server sends authorization state through Django Channels/WebSocket
→ Kiosk receives authorization
→ Kiosk transitions to the authorized/unlocked state
→ voter can proceed
→ authorization remains valid according to the existing state machine
→ invalid/expired/replayed authorization is rejected
→ relevant state is synchronized to the Officer Station
→ reconnect/resynchronization follows the existing architecture.

Once that workflow is working and tested, proceed to the next vertical slice.

==================================================
VERTICAL SLICE RULE
==================================================

A slice is NOT complete merely because:
- the model exists,
- the API exists,
- the WebSocket consumer exists,
- the template exists,
- or the page renders.

A slice is complete only when the actual user workflow can be executed
end-to-end through the application and its important failure cases have
been tested.

==================================================
ORDER
==================================================

Use the existing architecture and implementation plan to determine the
exact technical dependencies, but generally organize implementation
around complete workflows rather than technical layers.

The election setup workflow should become functional end-to-end first:

1. Create/save an election draft.
2. Configure election voters.
3. Configure positions and candidates.
4. Configure booths and devices.
5. Allocate voters.
6. Validate the election.
7. Save as draft / start election.

Then implement operational election workflows vertically:

8. Officer authentication and booth readiness.
9. Voter authorization.
10. Kiosk authorization reception and unlocking.
11. Ballot submission.
12. Transactional vote recording and authorization consumption.
13. Kiosk return to locked/ready state.
14. Real-time turnout and device synchronization.
15. Reconnection/state resynchronization.
16. Election closure.
17. Result publication.

Do not assume that the order above overrides the state machines or
architecture. Resolve dependencies using the existing locked documents.

==================================================
NO PREMATURE ABSTRACTION
==================================================

Do not build speculative infrastructure "for later."

Before introducing a service, abstraction, API, component, or utility,
identify which current vertical slice requires it.

However, do not duplicate code when an existing architectural component
already provides the correct abstraction.

Follow the existing coding standards.

==================================================
AFTER EACH SLICE
==================================================

Before moving to the next slice:

- run the relevant tests
- manually verify the workflow where appropriate
- inspect database state where necessary
- verify state transitions
- verify relevant invariants
- verify authorization boundaries
- verify WebSocket behavior where applicable
- verify failure/rejection paths
- confirm that the implementation still matches the locked architecture

Then record the completed slice and any discovered implementation issue
before proceeding.

# 1. Locked technical architecture

## Deployment and Ownership Model

Electra is a **self-hosted web application deployed over a Local-Area Network (LAN)** (e.g., `http://192.168.x.x:8000`).

The installation itself is the ownership and isolation boundary:

* **One Electra installation** represents one independent deployment for one institution/operator;
* **One PostgreSQL database** per installation (no cross-tenant sharing or cloud multi-tenancy);
* **One human Administrator** (`role = ADMIN`) per installation;
* **One central voter registry** scoped to the installation and shared across elections;
* **Multiple elections** belonging to the installation as a whole (strictly no `Election.owner` or per-user tenancy);
* **Multiple polling booths** with paired Officer Station and Voting Kiosk technical accounts.

## Backend

* Python
* Django
* Django Channels
* Daphne/ASGI
* PostgreSQL
* Django ORM
* Django session authentication
* Django CSRF protection
* `transaction.atomic()`
* `select_for_update()`

Development/demo:

```text
python manage.py runserver 0.0.0.0:8000
```

Daphne's ASGI integration will serve the Channels/WebSocket functionality.

No:

* React
* JWT
* Redis for the planned deployment
* Celery
* Docker/Kubernetes
* microservices
* offline voting
* multi-tenancy / SaaS / public registration

The SRS itself specifies Django, Channels, PostgreSQL/MySQL and WebSockets, with HTTP for transactional operations.

# 3. Core data model

The following is the model to implement.

## User / Account

Use Django's authentication system with a custom user model established at project creation.

Roles:

```text
ADMIN
OFFICER
KIOSK
```

### Administrator Account
* Exactly one human Administrator account exists per installation (`role = ADMIN`).
* Created dynamically during first-run setup (`UNINITIALIZED → INITIALIZED`).
* **Dynamic Identity Rule:** Never hardcode administrator usernames (`"admin"`), primary keys (`id == 1`), or default passwords. Admin resolution must be dynamic via `role == Role.ADMIN` to preserve architectural extensibility.

### Technical Accounts
An Officer and Kiosk are **technical authenticated identities** bound to physical `Device` records, not ordinary human accounts.

---

## Device

Represent an Officer Station or Voting Kiosk as a technical device identity.

Important fields:

```text
Device
    user
    device_type       OFFICER / KIOSK
    booth
    identifier
    credential_status ACTIVE / REVOKED
    created_at
    updated_at
```

The password is hashed by Django.

The identifier is stable.

If credentials leak:

```text
identifier remains
password changes
existing session is revoked
```

Credential rotation is allowed even while the election is active.

A physical computer can therefore be replaced:

```text
New computer
    ↓
Open browser
    ↓
Login with same device credentials
    ↓
Same logical Officer/Kiosk identity
```

---

## Booth

```text
Booth
    election
    name/number
```

Each booth has exactly:

```text
1 Officer Device
1 Kiosk Device
```

The database/service layer must enforce the one-to-one pairing.

Booths can be added before an election starts.

If a booth is removed before polling:

```text
remove booth
    ↓
find its ElectionVoters
    ↓
reallocate them
    ↓
validate allocation
    ↓
print/download updated voter-booth list
```

After the election becomes active, booth configuration is frozen.

# 4. Voter registry
## Voter

Keep one central voter registry.

Voter
    primary_registry_value
    name
    gender
    academic_group

The primary registry identity is not hardcoded as `student_id`.

The administrator configures which institution-defined identifier is the
primary registry identity, such as:

    Student ID
    University ID
    Admission Number
    another institution-defined identifier

The configured identity value is stored in `primary_registry_value` and is
the unique registry-level identity used to match existing Voter records
during imports and prevent duplicate registry records.

The configured primary registry identity must be unique within the central
Voter registry.

Do **not** create separate voter tables for:

* male/female;
* departments;
* classes;
* semesters;
* sections.

These are attributes/relationships used for filtering and eligibility.

```text
AcademicGroup

    type
    parent
```

Possible types:

```text

SECTION
DEPARTMENT
PROGRAM
SEMESTER
```

The important point is that the importer does not assume that `MCA` means department.

The administrator configures the import structure.

Example:

```text
Department
    ↓
Semester
```

with:

```text
MCA
 ├── Semester 1
```

For a school:

```text
Class
    ↓
Section
```

with:

```text
Class 10
 ├── Section A

```

The import mechanism therefore supports different school/college structures without hardcoding a particular institution's hierarchy.

# 10. Eligibility rules

Each position can have zero or more eligibility rules.

For example:

```text
UG Representative

Rule:
    academic_group ∈ {CSE, Mechanical, Civil, ECE}

Rule:
    gender ∈ {Female}
```

Semantics:

* multiple values **inside one rule = OR**
* different rules = AND

Therefore:

```text
(CSE OR Mechanical OR Civil OR ECE)
AND
Female
```

No arbitrary Boolean rule engine.

No OR-groups.

This is enough for:

* common positions;
* department representatives;
* class representatives;
* gender-specific representatives;
* UG/PG-specific positions;
* combined department + gender eligibility.

# 11. VoterAuthorization

Use:

```text
Authorization
    election_voter
    booth
    kiosk
    status
    created_at
    used_at
    cancelled_at
```

Status:

```text
ACTIVE
USED
CANCELLED
```

No automatic expiry.

### ACTIVE

One voter is currently authorized and has not successfully submitted the ballot.

### USED

The complete ballot was successfully committed.

### CANCELLED

Officer explicitly cancelled it, or the election was closed while it was active.

There is no `EXPIRED` state.

# 12. Vote

The persistent vote deliberately remains separated from voter identity.

Conceptually:

```text
Vote
    election
    candidate
    created_at
```

No:

```text
voter_id
election_voter_id
authorization_id
```

A multi-position ballot therefore creates multiple Vote records.

For example:

```text
one authorization
        ↓
Chairperson → Candidate A
Secretary → Candidate C
MCA Rep → Candidate F
        ↓
three Vote records
```

but they collectively represent **one accepted ballot**.

This follows the SRS's requirement that voting be server-validated and that the recorded vote not be directly associated with voter identity.

# 13. Kiosk runtime state

Keep runtime state separate from persistent election state.

Possible kiosk states:

```text
OFFLINE
NOT_READY
READY
UNLOCKED
VOTING
LOCKED
```

The exact transitions will be controlled by the server.

Important:

> `READY` means the server currently knows that the kiosk WebSocket is connected, the kiosk has reported fullscreen/readiness, and the kiosk is available for authorization.

No application heartbeat.

The SRS currently mentions heartbeat/liveness, but the locked implementation decision is to use the persistent WebSocket connection and its disconnect/reconnect lifecycle instead of an application-level heartbeat. The database remains authoritative, so this is a deliberate implementation simplification.

Use Channels.

Suggested groups:

```text
booth:<booth_id>

admin:<election_id>
```

Events include:


No voter identity should be sent to the Kiosk.

# 16. Transaction/concurrency architecture

This is one of the most important parts of the project.

All critical voting operations use:

```python
transaction.atomic()
```

and:

```python
select_for_update()
```

Use a consistent lock order.

For voting operations:

```text
Election
    ↓
ElectionVoter
    ↓
Authorization
    ↓
Kiosk/device where required
```

This prevents race conditions between:

* two authorization requests;
* authorization and election close;
* two ballot submissions;
* vote submission and another administrative operation.

---

# 17. Authorization transaction

When the officer clicks **Authorize**:

```text
BEGIN
    lock Election
    lock ElectionVoter
    lock Kiosk

    verify election is ACTIVE
    verify current time is within voting period
    verify voter exists
    verify voter belongs to this election
    verify voter belongs to officer's booth
    verify has_voted = false
    verify kiosk is connected
    verify kiosk is ready
    verify kiosk is fullscreen
    verify no ACTIVE authorization already exists

    create Authorization(ACTIVE)

COMMIT
```

Only after commit:

```text
WebSocket → kiosk.unlock
```

Use `transaction.on_commit()` for the event.

The officer should not receive a success response before the authorization is committed.

---

# 18. Election closure and race prevention

The election close operation must also lock the `Election` row.

Therefore:

```text
Vote transaction
    locks Election
```

and:

```text
Close Election transaction
    locks Election
```

Only one can proceed first.

### If vote gets the lock first

The vote can finish before closure.

Then close happens.

### If close gets the lock first

Election becomes `CLOSED`.

The subsequent vote sees:

```text
CLOSED
```

and is rejected.

This makes the boundary deterministic and prevents a vote from being accepted after closure.

---

# 19. Ballot transaction

The kiosk submits the **complete ballot** over HTTP.

For example:

```text
Position 1 → Candidate 3
Position 2 → Candidate 7
Position 3 → Candidate 4
Position 4 → Candidate 2
```

Backend:

```text
BEGIN

lock Election
lock ElectionVoter
lock Authorization

validate:
    election ACTIVE
    current time valid
    authenticated kiosk
    kiosk matches authorization
    authorization ACTIVE
    voter has not voted

for every submitted position:
    verify position belongs to election
    verify voter is eligible for position
    verify candidate belongs to position
    verify exactly one candidate selected for position

create all Vote records

ElectionVoter.has_voted = True

Authorization.status = USED

Kiosk = LOCKED

COMMIT
```

Only after commit:

```text
HTTP response → success
WebSocket → ballot.recorded
WebSocket → turnout.updated
```

If anything fails:

```text
ROLLBACK
```

Nothing is recorded.

This directly addresses the SRS requirement that failed vote commits roll back and that confirmation occurs only after database commitment.

# 20. Multi-page kiosk ballot

The kiosk UI will present positions as separate interfaces/pages.

Example:

```text
Position 1
Chairperson
[Candidate A]
[Candidate B]
[Next]

↓

Position 2
Secretary
[Candidate C]
[Candidate D]
[Next]

↓

Position 3
MCA Representative
[Candidate E]
[Candidate F]
[Next]

↓

Review
[selection summary]

[Submit Ballot]
```

The voter only sees positions for which they are eligible.

The pages do **not** cause individual database transactions.

The selections remain temporary in the kiosk/browser until the final submission.

Only the final **Submit Ballot** creates the database transaction.

Therefore:

> Multiple UI pages, one logical ballot, one authorization, one atomic commit.

# 21. Ballot failure/retry

If submission fails before the transaction commits:

```text
ElectionVoter.has_voted = false
Authorization = ACTIVE
Vote records = none
```

The kiosk should display:

> **Vote was not recorded. Please try again.**

It should not falsely claim success.

If the server committed the ballot but the response was lost:

```text
ElectionVoter.has_voted = true
Authorization = USED
Vote records exist
```

The kiosk reconnects and resynchronizes.

It then displays:

> **Vote recorded successfully.**

and locks.

This handles the important "commit succeeded but HTTP response was lost" case.

---

# 22. Kiosk reconnection

On every kiosk WebSocket connection:

1. Authenticate the Django session.
2. Identify the kiosk from the authenticated technical identity.
3. Derive its booth from the server-side device binding.
4. Fetch current election state.
5. Fetch kiosk runtime state.
6. Fetch any active authorization for that kiosk.
7. Determine whether the authorization is `ACTIVE`, `USED`, or `CANCELLED`.
8. Send authoritative state to the browser.
9. Never trust stale local browser state.

If the browser was closed after authorization:

```text
ACTIVE authorization
```

is recovered.

If the ballot was already committed:

```text
USED
```

is recovered and the kiosk remains locked.

If the officer cancelled it:

```text
CANCELLED
```

is recovered.

---

# 23. Fullscreen

The browser Fullscreen API is used as a **readiness signal**, not as an OS security mechanism.

Kiosk reports:

```text
fullscreen_entered
fullscreen_exited
```

If fullscreen exits:

```text
Kiosk → NOT_READY
```

and the officer cannot authorize another voter while the kiosk is not ready.

The browser cannot provide OS-level kiosk lockdown, and that remains outside scope as specified by the SRS. 

---

# 24. Election timer and automatic closure

No Celery, APScheduler or external scheduler.

Store:

```text
starts_at
ends_at
```

The browser displays the countdown.

Server-side operations always enforce the deadline:

```text
now >= ends_at
```

means:

```text
no new authorization
no ballot acceptance
```

A lightweight `close_if_expired()` service is called by election-related requests.

Connected clients can also trigger the expiration check at the displayed deadline.

When the server changes:

```text
ACTIVE → CLOSED
```

it broadcasts:

```text
election.closed
```

to connected stations/kiosks.

Admin can also manually close the election early.

This avoids introducing a scheduler solely to change one database status.

# 25. Election start validation

The **Start Election** operation is an important validation checkpoint.

Before changing:

```text
DRAFT → ACTIVE
```

the backend verifies:

### Election

* name exists;
* voting start/end times valid;
* current time is compatible with start;
* at least one position exists;
* every position has candidates.

### Booths

* required booth configuration exists;
* each booth has exactly one Officer device;
* each booth has exactly one Kiosk device;
* credentials are active.

### Voters

* eligible voters are enrolled;
* every ElectionVoter has exactly one booth;
* no invalid/duplicate allocation.

### Position eligibility

* all eligibility rules refer to valid academic groups/values;
* candidate/position relationships are valid.

### Runtime station requirement

# 27. One-active-session enforcement

Implement a small device-session mechanism rather than trying to infer active sessions solely from Django's session store.

Conceptually:

```text
DeviceSession
    device
    session_key
    created_at
    last_activity
    revoked_at
```

At login:

```text
lock Device
    ↓
check active session
    ↓
if active:
    reject login
    ↓
otherwise create DeviceSession
```

On logout:

```text
DeviceSession → inactive
```

Credential rotation/revocation:

```text
invalidate active session
close WebSocket
```

This satisfies the SRS requirement for only one active session per Officer Station/Kiosk.

31. Primary Registry Identity and Academic Structure: The system shall allow the administrator to configure the primary registry identity used to uniquely identify and match voter records during registration and import. For example, this may be Student ID, University ID, Admission Number, or another institution-defined identifier. The administrator shall specify this identity in the same manner as the academic-group structure/context during voter import. The configured primary registry identity shall be used for detecting existing voters, preventing duplicate registry records, and matching subsequent imports to existing voter records.

Implementation implication

Do not hardcode `student_id` or `university_id` as the Voter model's
identity.

The Voter model stores the configured identity value in:

    primary_registry_value

The administrator configures which institution-defined identifier this
value represents.

For example:

    Primary Registry Identity = University ID
    primary_registry_value = "UNI202600123"

or:

    Primary Registry Identity = Student ID
    primary_registry_value = "STU202600123"

The configured identity is used for exact matching of existing Voter
records and for duplicate prevention during imports.


Registry Configuration
├── Primary Registry Identity
│   ├── Field/column: University ID
│   └── Matching rule: exact match
│
└── Academic Structure
    ├── Type: Department
    ├── Context: MCA
    └── Child: Semester

For an institution where the primary identity is Student ID:

Primary Registry Identity = Student ID

For another institution:

Primary Registry Identity = University ID
Important distinction

The primary registry identity is different from the election identity.

Registry identity → identifies the person across imports/registry records.
Voter → the persistent master registry record.
ElectionVoter → that person's participation in a particular election.
has_voted → election-specific voting state.
Vote → contains no voter identity, preserving ballot secrecy.

So the matching flow becomes:

Import file
    ↓
Admin specifies primary identity
    ↓
Read configured identity column
    ↓
Match existing Voter by primary registry identity
    ↓
Existing voter → update permitted registry fields
New identity → create Voter
    ↓
Create/update academic-group associations

I would also make the configured identity unique at the registry level. If the admin selects University ID, two Voter records cannot have the same University ID.

One further design point: because your election configuration is frozen once ACTIVE, the primary registry identity configuration should also be treated as frozen for an active election, just like the academic structure and eligibility-relevant voter data.


Only if there is no replacement device should the administrator need to remove the booth—and that operation is restricted to the pre-election configuration phase.
